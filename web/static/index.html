The gap

Most quality tools give you opinions. Teams need proof.

AI writes code faster than anyone can test it. Code review checks the diff, but it can't tell you whether /users/42 really leaks another user's data. Scanners can tell you, but they bury the real issues under "possible" ones. Either way, somebody still has to reproduce every bug by hand.

AI code review

Reads the change and points out risks in the code. Useful, and it never runs the app.

→ “this looks risky”

Traditional scanners

Hit the app with payloads and report everything that might be a problem. Your team does the triage.

→ “this might be a problem”

QAX

Attacks the running app and reports a bug as confirmed only when the app actually misbehaves, checked against a control request.

→ “here's the request that proves it”
How it works

From a URL to a filed bug in five steps

These are the stages QAX streams live while it scans: you watch each one run, and nothing is hidden behind a spinner.

  1. Point it at your app

    A running URL. Add the source repo and an auth token if you want deeper coverage.

    input

  2. Map the surface

    QAX reads the code (Python, JS/TS, Go, Java and more) and checks the endpoints it finds against the live app.

    model · ground

  3. Probe and tour

    Deterministic probes attack the API. A real browser tours the UI and records JS errors and failed calls.

    probe · tour

  4. Prove or demote

    A finding reaches Confirmed only if the app misbehaves where a control request doesn't. Everything else becomes a lead.

    prove

  5. Fix and file

    Each finding explains why it matters and how to fix it, and can be drafted as a Jira bug with a test case.

    report · export
Confirmed vs leads

Two lists, on purpose

Confirmed findings come from deterministic probes: run the scan again and you get the same list. Leads come from AI investigation, the UI tour and dependency checks. They catch more, but they can vary between runs, so they're shown separately and never mixed in with the confirmed list.

Coverage

40 deterministic probes, each with a built-in control

Every probe compares an attack request against a benign one and only reports a bug when the difference proves it. On a well-written app, that's how QAX stays quiet.

Plus a browser UI tour (JS errors, failed requests, visual regression against a baseline) and dependency CVE and licence checks. Business logic is covered by a growing set of checks (negative amounts, stale access after revocation, date order, silent truncation, duplicated rows); open-ended workflow bugs that need a product oracle are still on the roadmap. Security & privacy

Safe to point at your own stuff

A tool that attacks apps should be careful about how it does it. These controls are built in and covered by tests.

Runs on your machine

QAX runs locally. Your code isn't uploaded anywhere. AI features call the model provider with your own API key.

Authorized targets only

A scan won't start until you confirm you own the app or are allowed to test it. Probes that write data are labelled as such.

Stays on your origin

Generated tests never send requests or your tokens to any host except the target you gave.

Nothing filed by accident

Exports are dry runs unless the server operator enables live export. A request can't force a live push.

Lockable API

Set QAX_API_TOKEN and every API call must carry it. Do this before exposing the server beyond localhost.

Leaves no mess

Test records use qax* names, and the report tells you exactly what QAX created on the target and what it cleaned up.

FAQ

Questions people ask first

How is QAX different from an AI code reviewer?

A code reviewer reads your changes and comments on them. QAX tests the deployed app: it sends real requests and reports a bug as confirmed only when the response proves it. The two work well together.

What does “confirmed” mean exactly?

A deterministic probe saw the app misbehave in a way a control request rules out. For example, a forged token gets HTTP 200 while no token gets 401. The same scan reproduces the same confirmed list.

Is it a replacement for a penetration test?

No. QAX covers a defined set of bug classes (listed above) automatically and repeatably. Most business-logic flaws and chained attacks still need a human. QAX has a first business-logic check, and more are on the roadmap.

Do I need an OpenAPI spec or the source code?

No, though both help. QAX can scan from a URL alone, using common-path discovery and a UI tour. With source it maps endpoints from the code and checks them against the live app.

Can it change data on my app?

Some probes create disposable records to test access control. They're labelled as writing data, use qax* names, and the report lists what was created and cleaned up. Only scan apps you're allowed to test, ideally staging.

What leaves my machine?

The scanning engine and the test runner run locally. The AI features (deeper investigation, test generation) send prompts to the model provider using your API key. Running tests sends nothing to the AI provider unless you turn on AI healing (--ai-heal), which sends the page of a failing step; selector discovery uses AI only with discover --ai. Jira or Xray only receive data if you configure credentials and enable live export.

Which stacks does it support?

QAX has been run on Python (Flask, FastAPI), Node/Express, Go/Gin and Java/Spring apps. The code reader also understands Ruby, PHP, C#, Kotlin, Rust and more, but those have been tested less.

How much does it cost?

Running it locally is free during early access. You pay your model provider for AI features: a quick scan typically costs cents or nothing, and a deep scan has measured around $0.40. Paid plans will come later.
